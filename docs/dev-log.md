### [2026-10-29] 评测集 CSV 缺空列导致字段左移，评测在汇总除法处崩溃
- **步骤**：第2步·带引用生成 + 首轮评测
- **现象**：首轮评测完整跑完 45 题后，在最后汇总处 `reject_refused / n_r` 抛 `ZeroDivisionError`——错误出现在流程终点，而不是出问题的那一刻
- **原因分析**：评测集 CSV 有 6 行（5 条拒答题 + 1 条混合题）漏写了空的"来源文档"列，`csv.DictReader` 解析后整行**左移一位**：source_doc 装进了 `"reject"`，type 列装进了备注值"考幻觉控制"。于是拒答题一条都没被 `type in ("knowledge", "reject")` 筛进来，n_r=0。除零只是症状，数据列错位才是病根，且错误暴露点距案发现场隔了 45 题与 7 分钟
- **解决方案**：① 修正 6 行数据补上空列；② `run_eval.py` 载入评测集时增加 schema 校验——type 不在合法值集合 {knowledge, task, mixed, reject} 或行字段数异常时，立即打印问题行 id 并退出（fail fast）；③ 汇总除法统一加零保护兜底
- **预防措施**：手工维护的 CSV/Excel 作为代码输入前，入口处必须先做 schema 校验，让错误第一时间带着行号暴露，而不是流到最深处才炸

### [2026-10-31] 画像抽取三连坑：单位换算、触发盲区、temp=0 的不确定性
- **步骤**：第4步·长期记忆（第7步期间用户提问"说180斤会入库吗"触发回归测试发现）
- **现象**：用户说"我体重有180斤"不入库；三天后说"我降到了120斤啦"不更新；同一句抽取在函数级成功、在服务端却返回空
- **原因分析**：① 抽取提示词只写"单位换算"指令时模型不执行——它看到"180斤"对不上 `weight_kg` 字段，按"不要猜测"原则宁可不抽；**指令说不动模型，示例一说就懂**。② 触发检测是纯关键词（"体重/身高"等），"我120斤了"这类量纲口语全部漏网。③ 最隐蔽：`temperature=0` 并不保证输出确定——"降到了120斤"处于模型"当前体重 vs 变化量"的决策边界，同句跨进程结果漂移。另附一次乌龙：改完提示词忘重启服务（reload=False），误判修复无效
- **解决方案**：① 提示词改为 few-shot 换算示例（含"降到了N斤=当前体重""胖了N斤=变化量拒抽"正反例）② 触发改为 关键词+正则 `\d+(斤|公斤|kg|米|cm|磅)` ③ 边界任务升级为 glm-4.7 关思考（失败降级 flash），把决策推离边界
- **预防措施**：模型的边界行为用**示例**推向一侧而不是用指令恳求；凡模型"在两个答案间摇摆"的任务，要么示例定型、要么直接换更强模型；提示词类改动后必须确认服务进程已加载新代码

### [2026-10-30] 拒答路径未接流式通道 + 降级与闸门的交互缺陷
- **步骤**：第5步·SSE 事件流
- **现象**：网页提问后助手气泡空白、看似"卡死"，实际后端请求早已正常结束（前端输入框已解锁）；另外 Qdrant 宕机期间所有知识类问题全部被拒答
- **原因分析**：① pipeline 的闸门拒答分支直接 return，绕过了 `on_delta` 流式回调——前端只收到 route 事件、收不到任何文本，气泡呈空白；② 检索降级到 BM25 时向量分全为空，拒答闸门把 top1=0 误读为"内容不相关"，将降级期间的全部知识题拒之门外。两个机制单独测试都正确，组合起来却把系统变成"哑巴"——典型的组合行为缺陷
- **解决方案**：① 拒答文本统一经 `on_delta` 推送，保证任何出口都有事件；② 闸门区分两种情形：有向量分时按阈值判定"不相关"；向量侧不可用（降级）时改用"是否还有任何检索结果"判定
- **预防措施**：流式系统里**所有出口路径（正常 / 拒答 / 异常 / 熔断）都必须推送事件**，漏一条前端就"静默卡死"；新增降级、兜底类开关时，必须排查它与下游判定逻辑（本例：降级 × 闸门）的组合行为，单测各自正确不代表组合正确

### [2026-10-30] LangFuse v5 接入的三连坑：三个"故障"里两个是查询方式制造的假象
- **步骤**：第6步·LangFuse 观测
- **现象**：① trace 查询 API 始终返回空，疑似上报失败；② 观测延迟数值只有几毫秒，疑似计时失真；③ 部分子观测延迟数分钟才出现，疑似丢失
- **原因分析**：逐一排查后三个问题全部出在**消费端（查询/认知）**而非生产端（SDK 上报）——① v2 查询接口要求 ISO 时间戳必须带秒和时区（`2026-10-30T01:00:00Z`），缺一节就被正则校验拒绝且**静默返回空**；② API 的 latency 字段单位是**秒**而非毫秒，4.558 实为 4.5 秒完全正常；③ OTel 批量导出器本身有分钟级延迟，属正常行为不是丢数据。期间还因"观测疑似全丢"反复重查，浪费了多轮排查
- **解决方案**：修正查询时间戳格式；确认延迟单位后所有数值立刻自洽；区分"导出延迟"与"导出失败"
- **预防措施**：排查可观测系统时**先验证消费端**（查询方式、字段单位、分页）再怀疑生产端——尤其当返回是"空"而不是"错"时，优先怀疑查询参数被静默拒绝；接入任何新 SDK 前先读一遍其 API 响应的字段文档，别用直觉猜单位

### [2026-10-31] 全量评测四连败：一个批处理任务能踩的坑全踩了
- **步骤**：第7步·全量评测
- **现象**（按时间序，四轮失败）：
  ① 首轮跑 75 分钟后在 hybrid 75/221 处被智谱 API 一次网络 500 直接炸掉整个进程——且外层 `| grep` 管道伪造了退出码 0，后台任务显示"成功"；② 修复重跑后串行太慢：2 小时只跑 40 行（裁判 glm-4.7 是思考模型，单次判卷 9.3s，占单题一半耗时）；③ 改并发 4 后吞吐 6 倍提升，但打穿 embedding-3 免费档限流——hybrid 组 224 次"降级到 BM25"，整组数据被污染；④ 第 4 轮 690 题全部跑完，收尾删临时数据库时 Windows PermissionError（SQLite 连接未关闭、文件句柄未释放）炸穿主流程，结果没落盘**全部丢失**；⑤ 重跑时发现 embedding 已被账号级限流（当日累计约 1500 次调用），等待 18 小时跨天仍未恢复
- **原因分析**：每个失败都是一类结构性缺陷——① 外部 API 无重试 + 管道吞退出码；② 资源画像没算（思考型模型当裁判的耗时）③ 无限流预算（并发×频次>配额）④ 无断点落盘（结果只存内存）+ Windows 文件句柄语义 ⑤ 单供应商依赖。共同根因：**把批处理当成了"一次能跑完的脚本"而不是会失败的分布式任务**
- **解决方案**（逐条对应）：chat 调用 3 次指数退避重试；裁判关思考（9.3s→3.9s）+ `EVAL_WORKERS` 可配并发（限流后降 2）；Checkpointer 逐题落盘 + 按 (id,mode) 断点续跑 + 单题异常记录不炸全局；临时库删除前 gc.collect()+重试；embedding 通道独立客户端切换硅基流动 bge-m3（供应商可配置），阈值按新模型重标定
- **预防措施**：批处理任务四件套——**重试、断点、隔离、限流预算**，缺一会在真实配额/网络下现形；`set -o pipefail` 或不经管道收退出码；Windows 下删被 SQLite 占用的文件前先回收连接；涉及付费/免费配额的调用做供应商级解耦

### [2026-10-31] 裁判通道余额耗尽的 429 被"失败兜底"静默吞掉，192 题整批误判 False
- **步骤**：第7步·微调三组对比评测
- **现象**：三组对比评测 A/B 两组判卷正常，C 组（LoRA+RAG）192 题判卷结果全部为 False、汇总正确率 0%——而答案明细抽查明显正确（如"新手每周3次全身训练"被判错）
- **原因分析**：judge() 的异常处理把一切失败都走"关思考重试→换模型降级→仍失败返回 False"的兜底路径。评测中途智谱账号余额恰好耗尽（A/B 判完、C 组开始的边界上），glm-4.7 每次返回 429"余额不足或无可用资源包"，降级模型同样失败，函数遂静默返回 False——**致命错误被兜底逻辑稀释成"正常判错"混进结果集**。账号级错误（余额/配额耗尽）与瞬时错误（网络抖动、瞬时限流）的可恢复性完全不同，异常处理却没有区分二者
- **解决方案**：① judge() 捕获 RateLimitError 且报文含"余额/资源包"时立即 raise——致命错误必须炸出来而不是返回默认值；② 新增 `--rejudge` 原位重判模式：保留已生成答案、只重走裁判，避免重新生成答案引入温度采样的不可复现性；③ 事故数据备份为 `_ft_checkpoint_47backup.jsonl` 留证，全量改用免费 glm-4-flash 三组同裁判重判
- **预防措施**：批处理的"失败兜底"必须区分**瞬时错误（重试/降级可救）与致命错误（继续跑只会批量污染数据）**，后者要在第一时间带上下文抛出；LLM-as-judge 流水线出报告前必须抽查判卷明细——全 0% 一眼可疑，但**部分误判**只有抽查能发现（本例若 C 组正确率是 40% 而非 0%，极可能直接进报告）
